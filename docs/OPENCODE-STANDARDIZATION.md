# Gravity standardization from OpenCode

Reviewed on **5 November 2026** against the public [anomalyco/opencode repository](https://github.com/anomalyco/opencode), default branch `dev`, at commit [`d0045aaab5872df54da8723a6c43453b61e1ee90`](https://github.com/anomalyco/opencode/tree/d0045aaab5872df54da8723a6c43453b61e1ee90).

This is a selected-source review of desktop file access, composer attachments, project selection, health, session execution, permissions and IPC architecture. It does not establish full OpenCode parity or review every source file. The recommendations adapt public design patterns to Gravity's existing Electron/React application; they do not require copying OpenCode code or changing frameworks.

OpenCode's reviewed native picker uses a 20 MiB selection budget and a renderer-scoped token. Its composer can use native image/PDF parts or path/staged attachments according to capabilities and destination. Gravity uses bounded extracted text for PDF/Office documents, keeping that input separate from native image parts and from the agent's project access.

## Applied in the current Gravity source

These describe the Gravity 1.9.0 source. Release validation and packaged-app results belong in the release notes; this document alone does not establish that those checks passed.

- **A dedicated + file picker.** Native multiple-file selection accepts regular files of any extension and returns opaque IDs for file context. No project is required. Cancellation leaves the current draft intact, late results are discarded if the originating draft changed, and rejected selections produce actionable messages.
- **Bounded file handling.** Up to four files or project excerpts and eight supported image inputs can be attached. Regular file inputs are limited to 10 MiB, within the combined 60,000-character text/context budget. UTF-8 and BOM-marked UTF-16 text is decoded; undecodable/unknown files provide metadata and at most the first 1,024 bytes as a hex preview. This is not full binary interpretation or native document upload. Images sent as images are PNG, JPEG, WebP or GIF, with an 8 MiB limit per image and 24 MiB combined encoded budget; the selected connection must accept images. The image icon/paste/drop require image support; + can provide an image's metadata/hex preview to a text-only connection. These intake paths are not yet one shared file pipeline.
- **PDF/Office extracted text.** PDF, DOCX, XLSX and PPTX readers accept at most 10 MiB per input and run in a separate owned process using the bundled runtime. PDF/PowerPoint are bounded to 50 pages/slides; Excel has 20-sheet/2,000-row/10,000-cell limits, with independent XML and archive-expansion bounds. Output must fit the combined character budget without silent truncation. Reader progress is cancellable, document chips distinguish extracted text, and original-byte revisions are checked before sending cached text snapshots. External resources, formulas and macros are not executed.
- **Literal preview and bounded OCR.** Clicking a file chip opens the exact extracted text or binary metadata/hex preview as literal text, without file-controlled HTML/Markdown rendering. **Scan PDF** explicitly invokes local Windows PDF rendering and OCR through Windows PowerShell 5.1 and an installed OCR language. It is PDF-only, with 10-MiB/10-page/1,800-pixel-dimension/60-second/60,000-character limits and cancellation; OCR shares the two-job reader limit. Recognition can be inaccurate or unavailable and does not preserve document visuals. The preview identifies OCR and asks the user to check names, numbers and tables.
- **Explicit access and snapshot semantics.** Native selection authorizes only the selected canonical regular file, including legitimate Windows Downloads/OneDrive redirects. File identity is checked while reading and SHA-256 is checked again before previewing/sending. Native-picker image input is signature-checked and captured as image data. Text or binary-preview snapshots are saved with the message as read-only context, without adding workspace authority. Outstanding IDs are bounded; chat switching retains accepted session selections, while renderer reload/restart restores metadata requiring a fresh selection. Native paths and picker IDs do not enter persisted drafts.
- **Encrypted owner-specific drafts.** Unsent text, images and project selections are saved per chat/new-project draft in OS-encrypted `drafts.json`, with 128-draft/64-MiB limits and no plaintext fallback. Restored file chips require reselection or removal before send. Saves track dirty owners and revisions so a slow/failed write cannot mark newer content saved; a new-chat handoff keeps its source until destination persistence succeeds. Failed saves from earlier chats are included in the close flush. Failure/timeout offers **Keep editing** or **Discard unsaved drafts**; corrupted files remain preserved.
- **Correct project selection.** Workspace's **Open folder** now uses the root project callback and selects the returned project, matching the successful selection behavior of the main project flow.
- **Honest connection feedback.** A failed request remains visible beside the composer even when the local service is running. Known sanitized error codes provide useful recovery actions; arbitrary provider output does not become the user-facing error message.
- **Clear connection direction.** **Connections** distinguishes normal Chrome, API/local providers and optional separate saved website profiles; separate-profile setup is collapsed on the overview. **Share models** is the desktop's outgoing local API for another app, distinct from upstream provider authentication. **Save & discover models** saves the upstream's advertised IDs without preset model guesses; timestamped response checks remain separate from discovery and service health.
- **Bounded ChatGPT verification.** Security verification waits use one owned browser and a bounded wait. Recovery offers normal Chrome sign-in while retaining the browser sandbox. Cancellation and browser/profile ownership remain explicit.

Main Gravity boundaries remain `src/` for UI, `electron/main.mjs`/preload for native IPC, `electron/store.mjs` for persistence, `electron/agent.mjs`/`permissions.mjs`/`workspace.mjs` for agent actions, and `electron/managed-bridges.mjs`/`web2api-setup.mjs` plus `bridges/` for managed services and providers. Existing Chat/Plan/Build modes and Ask/Auto edits/Full permission controls remain the user-facing model.

## Acceptance checks

Use isolated temporary profiles and fixture providers for automated checks. Record live account checks separately.

| Area | Required outcome |
| --- | --- |
| Picker cancellation | Clicking + then cancelling retains the draft and previous attachments; it neither creates a project nor sends a request |
| Standalone attachments | With no active project, decoded text, PDF/Office text and unknown-file metadata/hex previews attach as read-only context and survive in saved message history |
| Mixed selections | Usable text/PDF/DOCX/XLSX/PPTX extraction remains distinct from binary metadata previews; oversized inputs and exhausted structure/character budgets produce errors |
| Size and format limits | File counts, bytes, document structures/XML/archive expansion, combined context and image budgets are enforced in the backend; native-picker images with mismatched signatures are rejected |
| Changed or expired selections | A changed/deleted file fails before provider submission; arbitrary or expired IDs fail; pending work is cancelled when its draft changes, while accepted per-chat session attachments are retained |
| Preview/OCR | File-controlled markup remains literal; OCR requires explicit PDF selection and enforces byte/page/dimension/time/output bounds, with visible language/accuracy information |
| Draft recovery | Switching chats/reloading preserves the right owner; restored files block send until reselected/removed; save failures keep session content and require keep-or-discard handling on close |
| Permission boundary | A file attached outside the project does not permit agent reads, edits or commands in its containing folder |
| Image capability | A text-only connection cannot send images; changing connection before sending repeats capability validation |
| Project selection | Open folder both adds and activates the selected project; cancelling leaves the current project selected |
| Failure feedback | A running service does not hide a failed request. Known recovery codes have actionable messages, without raw provider output, tokens or browser URLs |
| Verification and cancellation | Security verification opens no overlapping recovery browsers, waits within its bound, cleans up owned work on cancellation and preserves working account setup |
| Prompt ownership | Recovery preserves the user's draft and does not silently resubmit a previously attempted prompt |

For the live ChatGPT check, the user completes any website challenge in the browser, then explicitly tests a response. A listening local server or successful model discovery does not prove account generation works. Repeated challenges can depend on website/account policy and browser/session state; automated fixtures cannot guarantee that the website will stop requesting them.

## Next implementation priorities

| Priority | Work | Completion standard |
| --- | --- | --- |
| P1 | Shared IPC and recovery contracts | Define request/response schemas and a central sanitized error-code registry consumed by native handlers, bridges and UI; reject malformed input at the native boundary |
| P1 | Unified attachment intake | Build on implemented per-chat drafts and converge picker, image paste and drop on one validation pipeline with explicit pending/cancelled/failed states; extend non-image paste/drop deliberately |
| P1 | Explicit service/setup/request transitions | Give each attempt an identity, ignore stale results, show account and request state independently, and settle cancellation once |
| P2 | Document-quality improvements | Build on implemented literal previews and bounded Windows OCR; improve recognition guidance and format handling while preserving limits and accuracy disclosure |
| P2 | Broader workspace and tooling consistency | Extend the existing review/Undo, project guidance and permission flows with shared session/tool contracts before adding more autonomous tools |

PDF/Office text extraction, literal previews, bounded local PDF OCR and encrypted per-chat drafts are implemented in the 1.9.0 source. Unified file paste/drop, a complete typed IPC migration and a broad architecture rewrite remain future work. This comparison does not establish live Gemini inference or a signed Windows executable. OpenCode's package structure is a useful reference, not a requirement to replace React with Solid/Effect or JSON persistence with SQLite.

## Review limits and related guides

Only public repository source was used for this comparison. No private OpenCode internals or user account data were inspected, and no CAPTCHA bypass, automated solving, stealth configuration or sandbox disabling is part of the standardization.

The reviewed `dev` commit is the source of the architectural claims above. The official [permissions documentation](https://opencode.ai/docs/permissions/) includes version-specific OpenCode 1 material and should not be assumed to describe every aspect of this reviewed development implementation.
